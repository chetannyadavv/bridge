# Bridge

A shared negotiation workspace for card disputes. Instead of a cardholder
and a merchant each filing paperwork into a black box and waiting weeks
for an answer, Bridge puts them at the same table: the same evidence
board, the same timeline, and the same settlement recommendation,
updating live for both sides at once — mediated by a transparent,
deterministic decision engine instead of a hidden adjudication process.

Built end-to-end across six sprints: a full-stack app with realtime
sync, a rule-based decision engine modeled on real dispute-resolution
workflows, and a working demo covering every possible outcome.

---

## What it does

1. **A cardholder opens a dispute** against a charge — pick a reason, done.
2. **Both parties join a shared workspace** for that dispute. Everything
   either side sees, the other sees too — same evidence, same timeline,
   same recommendation, no asymmetry.
3. **Evidence gets submitted** by either side, tagged by credibility
   (verified transaction record, GPS-confirmed delivery, timestamped
   receipt, customer statement, merchant statement, etc.).
4. **A rule-based Decision Engine** reads the dispute's reason code,
   validates each side's evidence independently, and produces a
   recommendation — Approve Refund, Reject Refund, Partial Refund,
   Request Additional Evidence, or Escalate for Manual Review — with a
   confidence score and a plain-language explanation, live, over
   WebSocket, as soon as evidence changes.
5. **Both parties accept** (independently — resolving requires both, not
   just one) and the dispute closes with a clear, fully-explained
   Resolution page: the outcome, the confidence, the reason code, the
   evidence considered, what was missing from each side, and next steps.

## Quick start

```
bridge/
  bridge-frontend/   React + TypeScript + Vite
  bridge-backend/    FastAPI + SQLAlchemy + PostgreSQL
  docker-compose.yml # Postgres + backend
```

**1. Start Postgres + the backend:**

```bash
docker compose up --build
```

Starts Postgres on `localhost:5432` and FastAPI on `localhost:8000`,
auto-creating the schema and seeding demo data (including four
ready-to-open scenarios, one per possible decision outcome — see below)
on first boot. Confirm it's up: `curl http://localhost:8000/health`.

**2. Start the frontend** (separate terminal):

```bash
cd bridge-frontend
npm install
cp .env.example .env   # points at http://localhost:8000 by default
npm run dev
```

Open `http://localhost:5173`.

**3. Try it** — from the Landing page, either open the pre-seeded live
dispute, or go to Analyst View and pick one of the demo scenarios below.
Use the role switcher in the header to see both sides of the same
dispute; open it in two browser windows to see the realtime sync live.

## Demo scenarios

Seeded automatically on first backend startup, so a judge or reviewer
can see every outcome without setting anything up:

| Scenario | Merchant | Outcome |
|---|---|---|
| Cardholder wins | TechGear Direct | **Approve Refund** — only the cardholder substantiated a claim |
| Merchant wins | Riverside Bistro | **Reject Refund** — merchant has proof of fulfillment, cardholder has nothing on file |
| Needs more info | Northgate Electronics | **Request Additional Evidence** — no evidence submitted by either side yet |
| Can't auto-decide | Downtown Parking Co | **Escalate for Manual Review** — dispute reason doesn't map to a known reason code |

All four are reachable from **Analyst View** in the running app. Their
recommendations are generated by calling the exact same engine code the
live app uses — not hand-written text — so what you see is exactly what
the app would produce if you built the same evidence yourself.

## Architecture

```
Cardholder ──┐                          ┌── Merchant
             │                          │
             ▼                          ▼
        React frontend  ◄── WebSocket ──►  React frontend
             │                                  │
             └──────────► FastAPI ◄──────────────┘
                             │
                ┌────────────┼─────────────┐
                ▼            ▼             ▼
           PostgreSQL   Decision Engine   Connection
                         (deterministic,   Manager
                          rule-based)      (rooms,
                                            presence,
                                            broadcast)
```

- **Frontend** — React + TypeScript + Vite, Tailwind v4. Plain React
  state (`useState`/`useCallback`/`useReducer`) throughout — no Redux,
  no React Query. `DisputeContext` is the single state store; a thin
  `src/services/` layer is the only place that talks to the network.
- **Backend** — FastAPI + SQLAlchemy + PostgreSQL. Business logic lives
  in `app/services/`; routes stay thin. WebSocket connection management
  is isolated in `app/websocket/`.
- **Decision Engine** — `app/decision_engine/`, a four-stage deterministic
  pipeline (Reason Code Registry → Evidence Validator → Decision Engine →
  Recommendation Formatter). No LLM, no external AI API — every output
  traces back to an explicit, testable rule. See
  `bridge-backend/README.md` for the full breakdown.
- **Realtime** — one WebSocket room per dispute; every mutation
  broadcasts a full state snapshot (not a diff) to everyone in the room,
  which is what makes reconnection trivial and concurrent-write
  correctness a non-issue by construction.

## Project structure

```
bridge/

    src/
      pages/            One file per screen (Landing, CreateDispute,
                         Workspace, Timeline, SharedEvidenceBoard,
                         SettlementPanel, Resolution, AnalystView)

      lib/                 DisputeContext (state), RoleContext (demo
                           role switch), utils
      types/                 Shared TypeScript types
  bridge-backend/
    app/
      main.py             FastAPI app, CORS, startup, exception handling
      models/              SQLAlchemy models
      schemas/               Pydantic request/response models
      services/                Business logic
      decision_engine/          The four-stage pipeline
      websocket/                 Connection manager, broadcast snapshot
      routers/                    REST + WebSocket routes

                          tests against the full API, a dedicated
                          dual-acceptance suite, and an end-to-end final
                          validation test
  docker-compose.yml
```

## Testing

```bash
cd bridge-backend
pip install -r requirements-dev.txt
pytest
```

72 tests: pure unit tests for every stage of the Decision Engine (no
database involved), full integration tests against the real API
(including live WebSocket connections via `TestClient`), a dedicated
suite for the dual-acceptance resolution flow, and one end-to-end test
that walks the exact workflow a judge would run by hand — create dispute
→ both parties join → submit evidence → confirm realtime sync → confirm
the Decision Engine's output → confirm the Resolution page has every
field it needs.

```bash
cd bridge-frontend
npx tsc -b && npm run build && npm run lint
```

## What's real vs. what's a deliberate placeholder

**Real:** dispute creation, evidence submission, realtime sync (with
tested reconnection and concurrent-write handling), the full decision
engine (deterministic, unit-tested, backed by a documented rule
registry), dual-party acceptance, and a Resolution page that surfaces
the engine's complete reasoning.

**Deliberately not built** (explicitly out of scope, not overlooked):
authentication (a role switcher stands in — self-declared, not
verified), LLM/AI-generated recommendations (the engine is rule-based by
design, with the seam for a future model swap already isolated), file
uploads (evidence is text-based), and notification/email systems.

## Sprint history

1. Frontend skeleton — routing, mock UI for every screen
2. Frontend made functional — in-memory state, no backend yet
3. Real backend — FastAPI + PostgreSQL, frontend wired to it via a
   dedicated services layer
4. Realtime collaboration — WebSocket rooms, presence, reconnection,
   concurrent-write handling
5. Decision Intelligence Engine — the deterministic rule-based engine
   described above, replacing earlier placeholder logic
6. Polish — a fully-realized Resolution page (the engine's full output
   was being computed since Sprint 5 but never displayed until now),
   demo data for every outcome, graceful failure handling throughout,
   and a round of bug fixes (dual-party acceptance, a recommendation-
   ordering race condition, and a WebSocket status race on rapid role
   switching)

See `bridge-frontend/README.md` and `bridge-backend/README.md` for
implementation detail on each half.
